| 3 | `living` | 進学したら、どこから通う予定ですか | `home` / `alone` / **`undecided`** | — |

**「分からない」を表す値**：`undecided` / `unknown` / `skip`
（`src/lib/matching.js` の `分からないことを表す回答` に定義。これらを理由に制度を除外しない）

### 各質問の用途

| 質問 | 制度の確認順（matching） | 行動計画（action） | ヒント（hint） |
| --- | --- | --- | --- |
| `grade` | ○ `mext-shugaku`（hs3）／`jasso-taiyo`（hs3）／`minkan`（hs3, graduate） | ○ 学年別に4種 | — |
| `schoolType` | ○ `school-genmen`（national/private/both） | ○ `check-school-site` | ○ `private` のとき |
| `living` | **×（意図的に使わない）** | — | ○ `alone` のとき |
| `familySupport` | ○ `mext-shugaku`（strong）／`jasso-taiyo`／`minkan` | ○ `ask-family`（`unknown`） | ○ `enough` のとき |
| `researched` | **×（意図的に使わない）** | ○ `learn-basics`（`not_yet`） | — |
| `careBackground` | ○ `care-leaver`（`yes` で strong、`no` で除外） | ○ `care-consult`（`yes`） | — |

`living` と `researched` を制度の確認順に使わないのは、**制度の公式条件と結びつかないため**です。
パーソナライズされている感じを出すためだけに制度の絞り込みへ使うことはしていません。
この設計と制度データの実態がずれると `tests/matching.test.js` が失敗します。

#### 改善候補（1件）：シナリオ8

**「難しいと思う」と「一部なら出してもらえそう」で、結果画面が完全に同一になる**

- 対応：**今回は変更しません。** 人の反応を見ずに細分化すると、根拠のない区別を作ることになります。

## 6. 安全性・情報格差の観点

### 回答しない自由

除外が働くのは `careBackground="no"` と明確に答えた場合のみです。

全10シナリオ × 4つの「分からない」系の値（`schoolType=undecided`／`living=undecided`／

## 9. 留学中に検証したい仮説

**以下はいずれも仮説であり、現時点で証明されたものではありません。**

### 仮説1

制度名だけを列挙するよりも、「なぜ確認すべきか」を回答と結びつけて示すほうが、
次の行動につながりやすいのではないか。

- 現状：Ver.1 は一致したシグナルの理由をカードに表示している（最大8件）
- 検証したいこと：理由の有無で、利用者が公式サイトを開く割合が変わるか

### 仮説2

確認先を1-2-3の手順で示すことで、情報を見つけた後の行動障壁を下げられるのではないか。

- 現状：案内（guide）4件すべてに「確認のしかた」を3手順ずつ表示している
- 検証したいこと：手順の有無で、実際に確認先へ到達する割合が変わるか

### 仮説3

センシティブな質問をスキップ可能にし、かつスキップしても情報量を減らさない設計にすることで、
必要な情報へのアクセスを妨げにくくなるのではないか。

- 現状：`skip` で除外しない設計。10シナリオで情報量が減らないことを確認済み
- 検証したいこと：答えたくない人が、実際に離脱せず結果まで到達するか

### 仮説4

制度の対象判定をAIに任せるよりも、公式情報への橋渡しとしてデジタル技術を使うほうが、
安全で信頼されやすいのではないか。

- 現状：Ver.1 は受給資格を一切判定せず、確認の優先順位だけを示している
- 検証したいこと：判定しないことが、不安につながるのか、安心につながるのか

## 10. 次の改善判断

**人の反応が得られていない状態では、大きなUI変更や制度追加を行いません。**

理由は次のとおりです。

- 結果画面の長さ（7,016〜8,601px）を短くする判断は、「長い」と感じる人が実際にいるか
  を確認してから行うべきです。情報を先に削ると、何が不要だったのか分からなくなります
- 制度を増やすと画面はさらに長くなります。長さの評価が済む前に増やすと、
  長さの問題なのか件数の問題なのか切り分けられなくなります
- 「難しいと思う」と「一部なら出してもらえそう」の区別を細かくすることは、
  公式条件に根拠がない区別を作ることになります

## 検証の再実行方法

```
npm test                      すべての自動テスト（シナリオ検証を含む）
npx vitest run tests/scenarios.test.jsx   10シナリオの検証だけ
```

シナリオの定義は `tests/fixtures/scenarios.json` にあります。
質問や選択肢を変更した場合、このファイルの回答値が存在しなくなると
`tests/scenarios.test.jsx` が失敗して知らせます。

### 画面の情報量（第5章の表）を取り直す

第5章の表は、本物のブラウザで実際に操作して数えたものです。取り直すときは
ターミナルを2つ使います。

```
1つめ: npm run build && npm run preview
2つめ: node scripts/collect-scenario-baseline.mjs
```

`npm run dev` に向けたいときは URL を渡します。

```
node scripts/collect-scenario-baseline.mjs http://127.0.0.1:5173/
```

1件ずつの詳しい内容も欲しいときは、書き出し先を指定します。

```
SCENARIO_BASELINE_JSON=./scenario-results.json node scripts/collect-scenario-baseline.mjs
```

このスクリプトは選択肢のラベルを `src/ShingakuNavi.jsx` の `QUESTIONS` から
読み取るので、画面の文言を変えてもスクリプトを直す必要はありません。
